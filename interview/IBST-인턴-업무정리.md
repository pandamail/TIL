## Phase 2 — Docker & Jenkins 인프라 구축 (2025.09)

### CBT Docker 자동 배포 시스템

**목표**: 웹 UI에서 버튼 클릭 한 번으로 학교별 CBT 환경(FE/BE/DB)을 동적 생성·배포하는 자동화 시스템

**구현 내용**
- Flask(`main.py`) 기반 REST API 서버로 Docker 환경 자동화
- 학교 등록 시 BE + DB 컨테이너 세트 동적 생성
- 학교별 `env.js` 파일 동적 생성 → 프론트엔드가 자신의 백엔드 주소를 자동으로 참조
- Caddy 라우팅 규칙 파일(`.caddy`)에 학교 정보 자동 추가 + `caddy reload`로 무중단 적용

**아키텍처 발견 과정**
- 초기 접근: FE/BE/DB 컨테이너 전부 띄우는 방식 → FE 컨테이너 `Restarting` 루프
- `docker exec`로 컨테이너 내부 직접 접속해 원인 분석 → `caddy` 실행 파일 자체가 없음
- 선임 운영 환경(`docker ps`) 분석 → FE 컨테이너 없이 **단일 마스터 Caddy**가 모든 요청 처리하는 리버스 프록시 구조 발견 → 아키텍처 전환

**트러블슈팅**
- `hosts` 파일에 가상 도메인과 VM IP 연결
- Caddy 자체 서명 인증서 Windows 설치 (`ERR_CERT_AUTHORITY_INVALID` 해결)
- `Caddyfile` CORS 헤더 규칙 추가
- `lsof -i :[포트]`로 포트 충돌 프로세스 식별 및 해결

### Jenkins 파이프라인

- Jenkins를 Docker 컨테이너로 설치 및 운영
- GitLab Webhook 연동 → 코드 push 시 자동 빌드 트리거
- Pipeline Script 작성 (Declarative Pipeline)
- GitLab 인증 토큰 만료/갱신 관리

### 배운 것

단순히 컨테이너를 띄우는 것을 넘어, 리버스 프록시를 중심으로 여러 서비스를 유기적으로 연결하는 현대적인 웹 서비스 아키텍처를 직접 설계·구축. 가설 수립 → 진단 → 근본 원인 파악의 디버깅 프로세스 체득.

## Phase 3 — CBT Playwright E2E 테스트 (2025.10 ~ 2025.12)

**목표**: CBT 시스템을 학생/관리자 두 시점에서 전 플로우 자동화 테스트

### 구현 내용

- 4단계 테스트 시나리오 작성: 로그인(step1) → 문제 설정(step2) → 환경 설정(step3) → 시험 응시(step4)
- `.env.test` 기반 환경별 설정 분리 (서버 주소, ID/PW 등)
- `--target` 옵션으로 특정 파일 단독 실행, `--ui` 모드 디버깅 활용
- `-g (grep)` 옵션으로 특정 테스트 케이스 선택 실행

### 고군분투했던 부분

처음 작성하는 E2E 테스트라 단순한 클릭·입력 자동화가 아니라, **비동기 로딩 대기**, **동적 UI 요소 선택자**, **테스트 간 상태 격리** 등 실전에서만 마주치는 문제들을 하나씩 해결했다. 특히 어떤 선택자를 써야 안정적인지, 어떤 시점에 assertion을 걸어야 하는지 감을 잡는 데 시간이 걸렸다.

### 핵심 트러블슈팅 — 리디렉션 무한루프 (약 1개월 소요)

**기간**: 2025년 11월 ~ 12월

**문제 현상**
- 좌석 선택 후 인증번호 입력 페이지로 이동하려는 순간, `/prelogin`으로 강제 튕겨나가는 현상
- 로컬에서는 100% 성공, Jenkins CI 환경에서는 Flaky Test(브라우저마다 결과 다름)
- 처음엔 당연히 내 테스트 코드 문제라고 생각했다

**1개월간의 삽질 과정**
- `waitForTimeout()`으로 대기 시간 늘려보기 → 근본 해결 안 됨
- Playwright 로그, 브라우저 콘솔 로그 대조해서 실패 지점 특정
- "비동기 타이밍 문제겠지"라는 가설로 테스트 코드를 계속 수정
- 그래도 Jenkins에서 간헐적으로 실패

**원인 — 기존 소스코드의 Race Condition**

선임 개발자와 페어 프로그래밍으로 프론트엔드 핵심 로직 `useCoreContextState.ts`를 집중 분석한 결과, **내 테스트 코드가 아닌 기존 소스코드의 버그**였음을 발견.

좌석 선택 정보가 **IndexedDB에 저장 완료되기 전에** `useEffect` 내의 인증 체크 로직이 먼저 실행되어 "인증 정보 없음"으로 오판 → `/prelogin` 리디렉션 유발.

더불어 `needRedirect`가 `true`인 상태에서 이미 `/prelogin`에 있을 때 `setNeedRedirect(false)`를 호출하지 않는 누락 조건이 있어, 상태가 계속 `true`로 유지되며 루프 발생.

```js
// 변경 전 — needRedirect=true이고 이미 /prelogin일 때 false로 못 바꿈
useEffect(() => {
    if(needRedirect && !(pathname === "/prelogin" || ...)) {
        setNeedRedirect(false)
        return navigate('/prelogin', {replace: true})
    }
}, [needRedirect, pathname]);

// 변경 후 — else 분기 추가로 /prelogin에서도 needRedirect를 false로 처리
useEffect(() => {
    if(needRedirect) {
        if(!(pathname === "/prelogin" || ...)) {
            setNeedRedirect(false)
            return navigate('/prelogin', {replace: true})
        } else {
            setNeedRedirect(false);  // 누락된 분기
        }
    }
}, [needRedirect, pathname]);
```

**해결 및 결과**
- 직접 코드를 수정한 건 아니었다. 대신 "어떤 상황에서 이 버그가 재현되는지"를 정확히 정리해서 프론트엔드 담당 정아름 연구원님께 보고
- 재현 조건이 명확하게 정리된 덕분에 연구원님이 원인을 빠르게 파악해 수정
- 테스트 코드도 단순 대기 대신 핵심 데이터(`student_sit`) 저장 여부 + 네트워크 응답 완료 체크로 고도화
- **한 달간 지속되던 Jenkins 빌드 오류 완전 해결**
- Chromium, Firefox, Webkit 전 브라우저 통과

**이 경험에서 얻은 것**

한 달 내내 내 테스트 코드 문제인 줄 알고 혼자 씨름했는데, 알고 보니 기존 소스코드의 버그였다. 혼자서는 해결할 수 없었던 문제였고, 결국 "내가 고칠 수 없는 문제"라는 걸 인정하고 버그 재현 조건을 명확히 정리해서 보고한 것이 해결의 열쇠였다. 해결됐을 때 가장 허무하면서도 가장 뿌듯했던 기억. E2E 테스트가 단순 기능 검증을 넘어 **실제 서비스의 숨은 버그를 드러내는 도구**가 된다는 것도 이때 체감했다.

## Phase 4 — SimMonitor / SIMPREC 개발 참여 (2026.01 ~ 2026.02, 약 5주)

**역할**: SimMonitor 기능 개발 + SIMPREC 백엔드 연동 안정화 (2인 공동 개발)

**기술 스택**: C# / .NET Framework 4.8 / WPF / WCF XML 파싱 / WebSocket / REST API / FastAPI / MySQL

### 배경

의료 시뮬레이션 교육 현장에서는 Laerdal LLEAP(SimBaby, SimMan) 시뮬레이터가 사용된다. LLEAP는 외부 시스템과의 자동 연동 기능을 제공하지 않아, 녹화 시작/종료를 교수자가 수동 조작해야 하고 임상 데이터가 영상과 별도로 관리되는 문제가 있었다.

- **SimMonitor**: LLEAP와 SIMPREC 사이 C# 미들웨어 — 시뮬레이터 이벤트를 실시간으로 파싱해 전달
- **SIMPREC**: 녹화 제어 + 학생 학습 관리 웹 플랫폼 (React / FastAPI / Docker)

### 내가 담당한 주요 작업

**① 이벤트/약물 한글 번역 추가**

LLEAP에서 넘어오는 이벤트·파라미터 명칭이 영문이라 모니터링 화면에서 읽기 어려운 상태였다. 한글로 출력되지 않거나 누락된 항목들을 확인하고, 이벤트·약물 번역 테이블을 추가·보완했다.

**② 웹 대시보드 실시간 스트리밍**

SIMPREC 웹 대시보드에서 시뮬레이션 진행 중 바이탈 사인과 임상 이벤트가 실시간으로 표시되도록 WebSocket 연동 작업을 진행했다.
- 진행 중 페이지를 열면 빈 화면이 표시되는 문제 → WebSocket 연결 시 현재 바이탈 스냅샷 + 최근 이벤트를 즉시 전송하는 초기 동기화 로직 구현
- 이벤트 중복 표시, 이전 세션 데이터가 새 세션에 잔류하는 고스트 이벤트 수정

**③ WCF 단일 파이프라인으로 구조 변경**

SimMonitor는 초기에 WCF 로그 파일과 tshark(패킷 캡처) 두 가지를 함께 사용하는 구조였다.
- **WCF**: 이벤트 수신
- **tshark**: 바이탈 실시간 추출 + 세션/시나리오 시작 감지 담당

SimMan 도입 과정에서 중복 이벤트, 누락 등 다양한 오류가 발생했고, 인턴 기간 끝자락에 윤상현 책임님과 함께 원인을 분석했다. 분석 결과, **tshark에서 추출하던 바이탈·세션 정보가 실제로는 WCF 로그에도 전부 포함되어 있다**는 것이 확인됐다. tshark는 실시간성 때문에 도입했던 것인데, WCF 로그만으로 필요한 모든 정보를 얻을 수 있었던 것이다. 이에 따라 tshark를 제거하고 WCF 단일 파이프라인으로 정리했다. (이벤트 UUID는 두 소스가 함께 동작할 때 중복 이벤트를 걸러내는 용도로 확인됐다.)

### 배운 것

두 가지 데이터 소스를 동시에 사용하는 구조에서는, 각 소스가 어떤 이벤트를 담당하는지 먼저 명확히 정리해야 한다는 것. 구조가 정리되고 나니 개별적으로 틀어막던 문제들이 한꺼번에 해소됐다. 근본 원인을 잡는 것과 증상을 패치하는 것의 차이를 직접 경험했다.

## Phase 5 — SIMPREC 백엔드 연동 안정화 (2026.01 ~ 2026.02)

**역할**: SimMonitor ↔ SIMPREC 간 실시간 연동 버그 수정

**기술 스택**: FastAPI (Python) / MySQL / WebSocket / React 19

### 내가 담당한 주요 작업

**① 모니터링 페이지 중간 접속 시 빈 화면 문제**

시뮬레이션이 이미 진행 중인 상태에서 모니터링 페이지를 열면 바이탈·이벤트가 아무것도 표시되지 않는 문제가 있었다. WebSocket은 연결된 이후의 데이터만 수신하기 때문이다.

WebSocket 연결 시점에 서버가 현재 바이탈 스냅샷, 최근 이벤트 100개, 녹화 상태, 세션 정보를 즉시 전송하는 초기 동기화 로직을 구현해 해결했다.

**② 이벤트 중복 표시 & 고스트 이벤트**

동일한 이벤트가 HTTP와 WebSocket 두 경로로 SIMPREC에 도착해 프론트엔드에서 2번 렌더링되는 문제가 있었다. 또 새 시나리오가 시작됐는데 이전 세션의 이벤트(CPR, 약물 투여 등)가 로그에 그대로 남아있는 고스트 이벤트 문제도 있었다.

이벤트 UUID 기반으로 중복을 걸러내고, 세션 시작 시 이벤트 히스토리를 초기화하는 방식으로 해결했다.

**③ 녹화 재생 시 바이탈 데이터 누락**

실시간 모니터링 화면에서는 바이탈이 잘 표시됐는데, 녹화를 재생할 때는 바이탈 데이터가 나오지 않는 문제가 있었다. 실시간 표시 로직과 DB 저장 로직은 연결되어 있었지만, 재생 화면에서 DB 데이터를 영상 타임라인에 연동하는 부분이 구현되지 않은 상태였다.

`session_vitals` 테이블의 시계열 데이터를 녹화 시작 기준 상대 시간(`relative_time_seconds`)으로 영상과 동기화해 표시되도록 구현했다.

### 배운 것

WebSocket처럼 연결 이후부터만 데이터를 받는 구조에서는, "중간에 접속하는 사용자"를 처음부터 고려해야 한다는 것. 실시간 데이터와 저장 데이터가 별개로 취급되는 경우가 많은데, 사용자 입장에서는 같은 데이터로 보여야 한다는 것도 이때 체감했다.

## 업무 방식

### TIL 작성

인턴 기간 내내 학습한 내용과 업무 경험을 GitHub TIL 레포에 기록했다. 트러블슈팅 과정, 아키텍처 분석, 회고 등을 문서로 남겨두는 습관을 이때 만들었다. 나중에 같은 문제를 다시 만났을 때 기록이 실제로 도움이 됐고, 이 인턴 업무 정리 문서도 그 기록들을 기반으로 작성됐다.

### AI 도구 활용

업무 전반에 걸쳐 Gemini, ChatGPT, Claude Code를 활용했다.

- **코드 이해**: 처음 접하는 C# 코드베이스(SimMonitor)나 낯선 로직을 파악할 때 AI에게 설명을 요청하며 이해 속도를 높였다.
- **문서 작성**: 아키텍처 문서, 트러블슈팅 기록 초안을 잡을 때 활용했다.
- **디버깅 아이디어**: 원인을 특정하기 어려운 버그에서 가설을 세우는 데 참고했다.

특히 SimMonitor / SIMPREC 개발 시기에는 대표님께서 **Claude Code Max Plan(토큰 무제한)**을 직접 제공하며 바이브코딩을 경험해보도록 투입하셨다. AI가 코드를 빠르게 생성해주는 환경에서, 코드 흐름을 이해하지 않고 진행했을 때 어떤 문제가 생기는지도 직접 겪었다. 결국 AI 도구는 이해를 대체하는 게 아니라 이해를 돕는 수단이라는 것을 그 과정에서 배웠다.
